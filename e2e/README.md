# End-to-end tests

Playwright specs that run locally only, in a visible (headed) Chromium window, against a production build that `pnpm test:e2e` starts itself with `pnpm build && pnpm start` (see `playwright.config.ts`). They are not part of `pnpm test` and are never pointed at a deployment.

## Running

1. Once: `pnpm exec playwright install chromium`.
2. Every time: `docker compose up -d db`, then `pnpm test:e2e`. One spec: `pnpm test:e2e e2e/auth.spec.ts`.

No `.env.local` is needed. The config gives the server its own environment, which overrides anything in `.env.local`:

- `DATABASE_URL` and `DATABASE_URL_UNPOOLED` point at the Docker `wardrobe_e2e` database, never at `wardrobe`, so local data is never touched.
- `APP_PASSWORD_HASH` is the base64 bcrypt hash (cost 4, for speed) of `E2E_PASSWORD` in `constants.ts`, a fixed password that only works on this throwaway server.
- `SESSION_SECRET` is random and new on every run, so a session from an earlier run never verifies.
- `OPEN_METEO_BASE_URL` points at the local Open-Meteo stub, `open-meteo-stub.ts`, which `playwright.config.ts` starts first as a second web server (`node e2e/open-meteo-stub.ts`, `http://127.0.0.1:3901`, ready when `/health` answers). It answers `/v1/forecast` with the saved Hamburg forecast (`src/lib/weather/fixtures/forecast-hamburg.json`) moved to today in the requested time zone, because the app refuses a forecast for another day, and lists the queries it received at `/__requests`, so `/today` never reaches the network (D-202). Node prints a harmless warning about the module type when it starts.
- Every other app variable (`BLOB_READ_WRITE_TOKEN`, `ANTHROPIC_API_KEY`, `CLAUDE_TAGGING_MODEL`, `CLAUDE_ANALYSIS_MODEL`, `CLAUDE_OUTFIT_MODEL`, `CLAUDE_ANALYSIS_EFFORT`, `MONTHLY_AI_BUDGET_USD`, `AI_CREDIT_USD`, `CRON_SECRET`, `FEATURE_SHOPPING_AI`) is set to an empty value, so values in `.env.local` never reach the e2e server: `@next/env` only fills variables that are undefined, and the app treats a blank one as unset. The list is `test/app-env-vars.ts`, which Vitest uses too. `E2E_TAG` is left alone: the smoke spec reads it in the test runner, not the server.
- Real credentials reach the server only from the shell that starts Playwright (`live-env.ts`, D-113): `BLOB_READ_WRITE_TOKEN` when the shell has it, and `ANTHROPIC_API_KEY` only when `E2E_TAG=1` is set as well. Playwright does not load `.env.local`, and the values are never printed. With a token or key passed, the tests that assume the server has none (`add.spec.ts`, Delete in `item-detail.spec.ts`, the two tagging tests in `review.spec.ts`, all of `relocate.spec.ts`, and the progress-page scan in `a11y.spec.ts`, whose unfinished run is then not inserted) skip themselves with that reason, so run the smoke spec on its own. `test/e2e-guards.test.ts` checks that every spec seeding relocation parts has this guard.

`global-setup.ts` runs once per run, after the server has started: it applies the migrations in `drizzle/` to `wardrobe_e2e`, empties every table (login attempts included, so the login rate limit never carries over between runs) and seeds the climate profiles and `app_settings`. If the database is unreachable it stops with a message saying to run `docker compose up -d db`.

Chromium accepts the `Secure` session cookie on `http://localhost`, so the auth specs run without HTTPS.

## Specs

- `a11y.spec.ts`: an axe scan (`@axe-core/playwright`, tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`) of `/login` and `/offline` signed out, then `/wardrobe`, an item page, `/stats`, `/settings`, `/settings/export`, `/settings/usage`, `/add` and `/add/review` with three seeded items, the not-found page of an unknown item id, `/relocate`, the print page of a seeded finished relocation run, the progress page of a seeded unfinished run (stopped by the configuration error, since the server has no API key; with `E2E_TAG=1` and a key the run is neither seeded nor scanned, D-113), the relocation not-found page, `/shopping` with two entries, `/settings/climate`, `/today` (Bologna's forecast from the stub), `/outfits` with one seeded outfit, `/outfits/new` and that outfit's page, `/outfits/new` again after an empty Save (its slot messages, at 1440 px light and 390 px dark); then each of the finished run's five tabs, and `/wardrobe`, the finished run, `/today`, `/outfits` and the outfit's page again at 390 × 844. The runs' snapshots are built with the real payload and chunk code. Any serious or critical violation fails the test; every page's violations are attached to the report. The rows are deleted afterwards.
- `auth.spec.ts`: redirects to `/login?next=…` when signed out; the PWA files and `/offline` stay public; `/api/*` answers 401 JSON; a wrong password shows the error; the right one sets the httpOnly, Secure, SameSite=Lax cookie and returns to `next`; with JavaScript disabled, a wrong password still shows the error and signing in still returns to `next` (D-054); logout from Settings; `/login` while signed in goes to `/wardrobe`; and a cookieless POST with a forged `Next-Action` header returns no app page and no item data (D-013); its canary item is deleted again right after.
- `export.spec.ts`: two seeded items; Settings links to `/settings/export`; the JSON download parses, has `version` 1 and exactly the keys of `EXPORT_JSON_TABLES` in order (every table but login attempts, D-135), and lists both items with their photos; the CSV starts with a BOM, has the expected header and one row per item; one processed-photo part is listed with its link (ZIPs are not downloaded: the seeded photo URLs are not on a Blob host); no sideways scroll at 390 px.
- `item-detail.spec.ts`: a confirmed and a pending item. The page shows the photo, the original link, the plan and location toggles, the form with Save and no Confirm, and the tagging model; a decision and a location change are saved at once and survive a reload without counting as edited tags; a rename is saved; Archive then Unarchive brings the item back as confirmed; Delete without a Blob token shows the configuration error in the dialog and keeps the item and its three photo rows, with none of them queued in `blob_cleanup` and its id not listed in `deleted_items` (D-234, D-238); a pending item offers Tag now and Fill in by hand, and Cancel returns focus; a malformed and an unknown id show the not-found page; no sideways scroll at 390 px. The tests run in order (the rename comes before Archive).
- `add.spec.ts`: the add page renders without a Blob token or an Anthropic key; picked photos are prepared and their source hashes checked (the check is held with `page.route` so the Checking state can be seen), then each photo and a toast report that uploads are not configured; no item row is created and no request reaches Blob storage (requests to the Blob API at `vercel.com/api/blob` are routed, recorded and aborted, and none may be made). The fixture JPEGs are generated with sharp while the spec runs.
- `add-tagging.spec.ts`: the add page's tagging controls with storage and Claude answered in the browser (`page.route` for `/api/blob/upload`, the Blob store's PUT, `/api/items/register` and `/api/items/<id>/tag`); the page, session, hash check and budget read are the real build. Two ready photos get the quote, the remaining budget and Start tagging; 21 get the batch offer; toasts stay off the bar at 390 and 1280 px, both stuck to the bottom (21 photos) and in the flow of a short page (2 photos); a BUDGET_EXCEEDED answer shows the budget alert and disables tagging; following a link while an upload runs opens the leave dialog, and Stay keeps the page; coming back to `/add` after leaving starts with an empty list, and leaving again does not ask. Screenshots go to each test's output folder and the HTML report.
- `climate.spec.ts`: Settings links to `/settings/climate`; filling in every Bologna month and saving clears its placeholder mark; an invalid row is explained and not saved; Bologna becomes the default and then Hamburg again. `afterAll` restores the Bologna row column by column (`updated_at` included) and whichever profile was the default.
- `relocate.spec.ts`: twelve confirmed items, one waiting for tags and one archived. The form estimates 12 items and says what is left out; Run starts a real analysis, whose first part stops with the configuration error (no API key); the spec then completes that analysis in the database with the shared fixture result and its packing rows, as if Claude had answered, so the cache key is the one the server computed. The form then offers the earlier result ("Unchanged since …"); an override is saved and survives a reload; "Apply AI decisions" fills in the undecided items and keeps the override; gaps go to the shopping list once and show there; a packing tick and an added extra survive a reload and the checklist prints, with the items no longer coming (the override's Leave, an applied Sell) under "Not bringing" (D-181); "Re-run anyway" starts a second run that stops the same way; at 390 px nothing scrolls sideways and the two rows of result tabs stay inside the tab list. Skipped when the shell passes an API key (D-113). Every analysis it started, its calls, shopping rows and items are deleted afterwards.
- `outfits.spec.ts`: three confirmed items named with the token "Outspec" (a sweater, jeans and boots). Save on an empty `/outfits/new` points out the missing top and name at their places; the slot pickers (searching for the token) fill top, bottom and shoes; name, occasion, a temperature range with a comma decimal ("12,5"), "Fine in rain" and a rating are saved, and the outfit is listed with them and "Never worn". "Wore this today" on the list logs a wear (the database's `wear_count` becomes 1) and Undo in the toast takes it back (0); a second press on the same day says "Already logged" and counts once. The item page shows "Once", "+1 worn today" makes it "2 times" and Undo "Once" again. Deleting the outfit from its page (after the confirmation) leaves the three items and the wear count. At 390 px the builder, the picker and the list do not scroll sideways. Its outfits, wear logs and items are deleted afterwards.
- `review.spec.ts`: seeds a tagged item (with a low materials confidence), a pending item with a stored tagging error and a plain pending item, all pointing at a local icon instead of Blob. Editing the name and adding a season, then confirming, leaves the item `confirmed` with both fields in `user_edited_fields`; the stored error shows with Retry; Tag now without an API key shows the error and leaves the item `pending_tagging`; an item filled in by hand ("Fill in by hand", Save and confirm) shows five "Default, not checked" notes and, after Keep on Windproof, is confirmed with `ai_raw` and `tagging_error` empty, the fields set in it and Windproof in `user_edited_fields` but not the untouched warmth, waterproof, insulated and breathable (stored at 3, off, off and unknown, D-232), and no `ai_calls` row, and an item linked to a (processed) batch row does not offer the button; no sideways scrolling at 390 px; the bulk "Tag N waiting items" control quotes the waiting items, and running it without an API key leaves each card with its error and Retry (screenshots at 1280 and 390 px). The seeded rows and the batch row are deleted afterwards.
- `shopping-advice.spec.ts`: with `FEATURE_SHOPPING_AI` off, as the e2e server always runs, `/shopping` shows a seeded entry but no "What to buy next" section; `POST /api/shopping/advice` with `{}` and with `{ "force": true }` answers 404 `{ ok: false, error: { code: "NOT_FOUND", message: "Shopping advice is turned off." } }`; Settings shows Shopping advice as Off; nothing scrolls sideways at 390 px. The seeded entry is deleted afterwards.
- `shopping.spec.ts`: at 390 px, an entry added by hand (category, priority, quantity, prices, timing, specs) shows its price range and timing; its status is saved at once and survives a reload; an owned item is linked through the search picker and survives a reload; the entry is deleted after confirming. Its rows and item are deleted afterwards.
- `smoke.spec.ts`: the whole path against a real Blob store, skipped ("needs BLOB_READ_WRITE_TOKEN in the shell") unless the shell has the token: sign in, upload two JPEGs generated with sharp, wait for "2 of 2 photos uploaded" and the original, processed and thumbnail rows, open the review page and confirm both (filled in by hand, or with `E2E_TAG=1` and `ANTHROPIC_API_KEY` tagged with Tag now and confirmed), see both cards on `/wardrobe`, filter by the first item's category, open it and set its plan to Donate. `afterAll` deletes every blob the run uploaded or the server wrote for its items (`del()` with the shell's token; the browser's upload answers are recorded too, in case registration failed), then the rows. Run it alone: `BLOB_READ_WRITE_TOKEN=… pnpm test:e2e e2e/smoke.spec.ts`.
- `today.spec.ts`: a 17-item wardrobe (the shared outfit fixtures, located in Bologna) and the seeded home city Bologna. `/today` names the day and the city, shows the weather card with the "Weather data by Open-Meteo.com" link, and the stub's `/__requests` proves the server asked the stub for Bologna in Europe/Rome. Without an API key, "Suggest outfits" shows the configuration error and no `ai_calls` row is written (skipped with a key, D-113). A complete suggestion for today inserted as if Claude had answered (the real prompt version and the fixture result) shows three cards; Save makes one outfit of source AI and becomes "Open saved outfit", also after a reload; "Wore this today" logs the second outfit's items with today's weather and Undo takes it back. With a second stored suggestion, "Wore this today" on the third card at 1280 × 720, 1440 × 900 and 390 × 844 leaves that card's Save clickable under the Undo toast (a trial click, which fails while the toast covers it), and Undo takes each wear back. On a phone the Wardrobe tab marks `/today` with `aria-current="true"`, reached from Settings and from the wardrobe header alike, and says "page" only on `/wardrobe`; on a desktop the sidebar's Today row says "page" on `/today` with no primary row marked, Outfits says "true" on `/outfits/new`, and Wardrobe "true" on `/stats` (D-218, D-230). Settings, Home city, switched to Hamburg moves `/today` to Hamburg's day and weather, then back to Bologna. Its items, analyses, outfits and wear logs are deleted and the home city restored afterwards.
- `stats.spec.ts`: seeds items that meet three of the six winter rules and nearly meet the other three (plus a pending and an archived item); the totals match the database, the category and weather counts are right, each rule shows Ready or what is still needed with links to its evidence items, items marked Donate and archived items are never linked, and the page does not scroll sideways at phone width; an evidence link opens the item, and after it is marked Donate there, Back shows the rule as missing (the page read again, D-107). It fails at once if another spec left tagged or confirmed items behind.
- `usage.spec.ts`: Settings links to `/settings/usage`; the month-to-date total and the Tagging row match figures read from the database (other specs may log calls of their own); at 390 px the tables scroll inside their own box, not the page.

- `wardrobe.spec.ts`: 30 rows scoped by the brand token "wardspec"; chip counts and a category chip; the Untagged chip; search; sort; the filter panel's waterproof filter with focus back on Filters; opening a card and Back restoring the URL and results; going back after archiving on the item page (through its back link and through the browser's Back) shows the list read again (D-107); at 390 px, two columns and no sideways scroll. The rows are deleted afterwards.

Apart from the smoke spec, no spec calls Claude or Blob, and none reaches Open-Meteo; real tagging, uploads, relocation runs, outfit suggestions, shopping advice and the live forecast are live checks (HANDOFF.md).
